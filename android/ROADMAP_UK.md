# LowTube Android — ціль і план перенесення

Дата початку: 2026-11-14
Базова кодова база: WinForms-версія з гілки `main` (`8c599ab`)
Робоча гілка: `feat/android-full`
Статус станом на 19.11.2026: окремий Kotlin/Compose Android-проєкт збирається як один варіант застосунку для minSdk 23; каталог, локальна бібліотека, Media3 плеєр, process-death/background playback state і власна transfer queue мають bounded перевірки на API23 AVD та фізичному Android13 пристрої. API-різниці обробляються всередині цього APK, із сумісними шляхами для API 23; окремої «новішої» версії застосунку поки немає. Обмежений direct-stream playback прийнято для окремих публічних fixture на обох API, але live `s`/`n` challenge, інші client responses, повний набір форматів і всі ролики не прийняті. Android13 підтверджує PiP і повернення process-death state; API23 підтверджує state restoration і background MediaSession без перевірки чутного звуку. Профільний Google sign-in використовує системний account picker та Google AuthorizationClient; окремий `youtube.readonly` → YouTube Data API v3 має кодовий потік. Реальний OAuth/API acceptance чекає developer-owned Google Cloud config. Повний паритет із Windows не досягнуто.

Оновлення напряму продукту від 2026-11-17: Android має бути самостійним повноцінним YouTube-клієнтом LowTube, у стилі окремого клієнта на кшталт ReVanced, але без модифікації чи перепакування офіційного застосунку YouTube. Основна навігація: **Пошук**, **Для вас/Рекомендації**, **Підписки**, **Профіль**; локальні можливості LowTube — у меню **Ще**, крім еквалайзера, який на Android не переноситься за прямою вказівкою користувача. Цей напрям замінює попередній план із вкладками Library/Settings у головній навігації.

## Ціль

Створити окремо встановлювану Android-версію LowTube як самостійний клієнт YouTube із Google-авторизацією та знайомими сценаріями основного YouTube-клієнта. Перенести **всі функції PC-версії**, крім Android-еквалайзера, або надати перевірений Android-еквівалент із чітко описаними системними обмеженнями. Windows-застосунок лишається незалежним і працездатним. Android ніколи не патчить, не підміняє і не перепаковує застосунок YouTube.

## Цільові пристрої

- Мінімальна система: **Android 6.0 Marshmallow (API 23)**.
- Це одна кодова база й один Android APK із спільним набором продуктових функцій; виклики API, дозволи й окремі системні можливості можуть мати різні внутрішні реалізації за версією Android. Функцію, яка недоступна на API 23, не вважати підтриманою без сумісного fallback.
- Новіші системи підтримуються; функції з новіших API мають мати перевірений fallback для API 23, якщо ця функція потрібна для повного сценарію.
- Перевіряти API 23 та актуальну Android-систему, дозволи, мережу, сховище, життєвий цикл, аудіофокус і фонове відтворення.
- Підключений тестовий пристрій користувача: Redmi Note 8 (2021); Android 13 / API 33, `arm64-v8a`. Системні властивості пристрою зараз показують `TrebleDroid vanilla`; ADB авторизований, встановлення APK проходить.
- Ресурсний профіль: локально вимірювати CPU time, PSS/RSS і доступну RAM у важливих сценаріях через `tools/Measure-ResourceUsage.ps1`; див. [ANDROID_RESOURCE_PROFILE_UK.md](ANDROID_RESOURCE_PROFILE_UK.md). Не передавати статистику назовні чи записувати пошукові запити/URL.
- Settings тепер має ручний локальний 5-секундний замір CPU процесу, PSS/RSS/peak RSS і доступної системної RAM; замір перевірено на Redmi Note 8, результати лишаються на пристрої. Цей екран не запускає фонове опитування.
- Під час ручних тестів відтворення запускати відео лише коли змінюється логіка/поведінка самого плеєра; UI, бібліотеку та каталог перевіряти без playback. Не запускати відео до кінця: обмежуватися першими 2 хвилинами або менше, якщо сценарій уже підтверджений.
- Під час роботи залишати LowTube відкритим на передньому плані підключеного Redmi Note 8, щоб користувач міг спостерігати за процесом. Тести, що переключають активний екран або instrumentation-процес, за можливості запускати на API23 AVD; після будь-якої перевірки на телефоні повертати LowTube на передній план.
- 17.11.2026: зареєстровано системне відкриття YouTube-посилань через `ACTION_VIEW`/`BROWSABLE` (youtu.be та основні домени YouTube). Валідні посилання на відео, Shorts, трансляцію, плейлист чи канал направляються у внутрішній пошук; автоматичного запуску відео немає. Debug APK зібрано й оновлено на фізичному Android13, але запуск тестового intent host policy заблокувала; API23/API33 runtime acceptance лишається відкритим.
- Пошук: додано список останніх 12 текстових запитів, локальний пошук за префіксом і очищення списку. Запити лишаються у приватному SharedPreferences застосунку; URL/схеми посилань не зберігаються. Збірка пройшла 17.11.2026; перевірка UI на API23/API33 ще потрібна.
- Гостьові Home recommendations: Settings мають тему й 12 мов пошуку з PC списку; введення теми обмежено 200 символами; query має мовний суфікс та окремий UI language context. ViewModel кешує до чотирьох Home first-pages у пам'яті за locale/topic/search-language key і показує застарілі картки під час ручного refresh. На API23 перевірені Settings, dropdown та Home→Search→Home відновлення карток; зміна query в мережі та пагінація ще приймально перевірити.
- Персоналізація For You: з 17.11.2026 гостьові рекомендації локально чергуються з новими відео з кешу каналів користувача; дублікати видаляються, timestamp зберігається при читанні кешу, SQLite читається у фоновому IO dispatcher. Порядок ще не прийнято на фізичному API33/API23. Це локальна евристика; офіційний YouTube Data API не відкриває повний персональний home feed.
- Локальна стрічка підписок: публічні PC Atom feeds на Library з explicit batch максимум 6 каналів, до 3 паралельних запитів за профілем, 15 с timeout, 2 MiB/канал, до 30 записів/канал і 3000 у кеші. Якщо Atom endpoint відмовляє (API23 повернув HTTP 500), використовується перевірений InnerTube channel browse fallback; записується джерело fallback і коротка причина помилки. Ручне оновлення та профілі швидкості збережені. Додано Android WorkManager periodic task лише для локальних підписок і за наявності мережі: інтервали профілів 30/15/15 хв, а пакети 2/4/6 каналів та паралельність 1/2/3. Android має мінімум 15 хв для periodic work, тому швидкий профіль не може запускатися частіше; фактичний час може відкладати система. Unit-тест профілів і scheduler instrumentation пройшли на API23 та фізичному API33: перевірено реєстрацію, мережеву умову, idempotent startup та заміну профілю; після тесту LowTube повернули у foreground. Реальний періодичний мережевий цикл, перезавантаження пристрою та Doze/background limits ще перевірити.

## Принципи перенесення

- Зберігати англійську мову типовою, український і російський каталоги, світлу/темну теми та локальні дані.
- Kotlin-проєкт обрано як повністю нативний стек; поведінку та правила PC переносити у Kotlin, не підключати desktop assembly.
- Android UI, медіаплеєр, робота зі сховищем, сервіс відтворення, фонові задачі й доступ до облікового запису повинні використовувати Android-сумісні API.
- Не імпортувати автоматично Windows cookies, браузерні профілі, OAuth секрети чи приватні діагностики. Android-вхід потребує окремого безпечного потоку з явною згодою користувача.
- Зберегти Windows і hybrid desktop-варіанти незалежними, доступними для запуску та збірки.
- Не видавати за Android-паритет те, чого немає в Android: для кожного обмеження має бути діагностований еквівалент або чітка причина недоступності.

## Ціль інтерфейсу та меню

- Навігація першого рівня містить лише Search, Recommendations/For you, Subscriptions і Profile. Library, Queue, Downloads, Settings, діагностика, історія, локальні плейлисти та інші перенесені можливості LowTube відкриваються з меню **Ще**. Android EQ відсутній.
- Зберігати максимально знайомі мобільні сценарії та розташування основних дій, додаючи лише потрібні для LowTube зміни: чергу, локальні списки й історію, завантаження, вибір якості/кодека/доріжок, audio-only, діагностику та налаштування.
- Застосунок має власне ім'я та ідентичність LowTube; не використовувати логотип/ресурси YouTube так, щоб створювати враження офіційного застосунку. Офіційні правила YouTube API вимагають чіткого джерела контенту та обмежують імітацію основного browse UX; якщо обраний API-потік підпадає під ці правила, межі візуального наслідування треба звіряти з ними. Див. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies) і [Branding Guidelines](https://developers.google.com/youtube/terms/branding-guidelines).
- Зберегти EN/UK/RU, темну типову тему й ручний вибір світлої теми. Еталон — мобільний YouTube, компактний екран і керування однією рукою; Android-відступи й власний бренд LowTube лишаються читабельними.
- Новий shell має чотири основні вкладки, локальну стрічку підписок і меню **Ще** для бібліотеки/черги/завантажень/налаштувань; фізично переглянуто вкладки Search, For you, Subscriptions, Profile і вміст More на Android13 без запуску відео. На API23 AVD відкрито Profile у новому shell без помилок; повний shell acceptance ще треба пройти. Profile має Credential Manager sign-in/switch/sign-out; Subscriptions має дію окремої згоди й ручної синхронізації YouTube `youtube.readonly`. Поточний фізичний екран після встановлення — Subscriptions; Google OAuth/API flow не перевірено через відсутній Cloud config.

## Google-акаунт і межі YouTube API

- Профільний Google sign-in та доступ до приватних YouTube-даних — різні потоки: Profile показує системний Google account picker, потім використовує Google AuthorizationClient зі scopes `openid/email/profile` і bounded OpenID UserInfo запит. YouTube subscriptions окремо запитують `youtube.readonly` consent. Не збирати пароль і не імпортувати cookies; access token живе лише в пам’яті запиту, не зберігається й не логується. Profile поля зберігаються локально; це не серверна перевірка ID token.
- Поточний Profile/AuthorizationClient flow і YouTube AuthorizationClient consent реалізовані окремо. Для роботи власник LowTube має зареєструвати Android OAuth client для `com.lowtube.android` із SHA-1 відповідного debug/release сертифіката та ввімкнути YouTube Data API в Cloud project. Web client ID у profile flow більше не використовується. Runtime OAuth/API acceptance чекає developer-owned configuration; користувачеві не потрібно створювати власний Cloud project.
- Обраний напрям, щоб кінцевому користувачу не довелося створювати Google Cloud project: LowTube має використовувати OAuth-конфігурацію власника застосунку, підготовлену один раз для release-збірки; користувачеві залишаються звичайний Google sign-in і явна згода на YouTube scope. Це переносить налаштування на власника/оператора LowTube, але не скасовує реєстрацію Android package+signing certificate, OAuth client та YouTube Data API. Client ID не є секретом; client secret не можна вбудовувати в APK. Див. [YouTube API authorization](https://developers.google.com/youtube/data/guides/authentication) та [Google Sign-In best practices](https://developers.google.com/identity/siwg/best-practices).
- MicroG не вбудовувати в LowTube: GmsCore є системною заміною Google Play Services, для повної роботи очікує підтримку signature spoofing у ROM/системі та встановлюється як системний сервіс. Він не створює OAuth client для LowTube і не вмикає YouTube Data API, тож не знімає поточну зовнішню вимогу. Див. [microG overview](https://github.com/microg/GmsCore/wiki) та [microG installation](https://github.com/microg/GmsCore/wiki/Installation).
- Не підміняти офіційний flow входом через вбудований WebView, OAuth client ID іншого застосунку чи автоматичним вилученням браузерних cookies. Без власної LowTube OAuth-конфігурації Profile має показувати зрозумілий setup state, а гостьові можливості залишаються доступними.
- YouTube Data API v3 синхронізація `subscriptions.list?part=snippet&mine=true` з bounded пагінацією реалізована, але runtime потребує ввімкненого API в Cloud project та користувацької згоди. Access token використовується тільки в пам’яті запиту. Список email-scoped, очищається після 30 днів і при sign out; sign out видаляє локальні Profile поля і намагається відкликати grant через Google revoke endpoint, коли доступний token. API має лише read-only scope: відписування/керування remote subscription через LowTube поки немає.
- Офіційний YouTube Data API v3 не повертає список відео, персонально рекомендованих поточному користувачу; гостьова тематична стрічка та локальні підписки не є її еквівалентом. Див. [YouTube Data API revision history](https://developers.google.com/youtube/data/revision_history).
- Поточний пошук/стрічки використовують приватні веб-ендпоїнти; сумісність, доступ до акаунта й відповідність обраного способу отримання даних правилам треба переглянути до обіцянки повноцінної стабільності. OAuth не надає дозволу обходити обмеження API/клієнта.

## Етапи

1. **Інвентаризація:** скласти чекліст кожного PC-сценарію з джерелом у коді, даними, станами помилок та критерієм перевірки.
2. **Рішення про стек — виконано:** Kotlin + Jetpack Compose, AndroidX Media3 та окремий Kotlin backend; не переносити WPF/WinForms UI чи mpv IPC як desktop-компоненти.
3. **Окремий Android-проєкт — почато:** Kotlin/Compose проєкт із `minSdk 23`, `compileSdk/targetSdk 36`; додані Media3 1.11.0 (ExoPlayer, HLS, DASH, UI, MediaSession) і Coil. Debug APK успішно збирається та встановлюється на авторизований фізичний Android 13/API33 телефон.
   **Google account/subscriptions — реалізація готова, runtime acceptance чекає owner configuration:** Profile використовує system account picker + AuthorizationClient/OpenID UserInfo; Subscriptions окремо просить `youtube.readonly` та читає `subscriptions.list?mine=true`. Локальне сховище email-scoped, має 30-денне очищення й видалення при sign out. Власник має зареєструвати Android package/signature OAuth client і ввімкнути YouTube Data API; після цього потрібні реальні sign-in, consent і sync перевірки на API23 та API33. Sign-in не є серверно перевіреною автентифікацією.
4. **Каталог:** пошук, рекомендації, підписки, акаунтні стрічки, синхронізація, історія, канали, списки/плейлисти, Shorts і bounded paging.
5. **Медіа:** відео/audio-only, якість та формати, субтитри/доріжки, черга, наступне, resume, seek, аудіофокус, background/notification controls, recovery і діагностика.
6. **Локальна бібліотека:** локальна історія, підписки, плейлисти, resume, сумісний імпорт/експорт даних і обмежена пам'ять.
7. **Завантаження:** усі формати та правила вибору PC, черга, обмеження швидкості, прогрес, скасування/retry/resume і Android Storage Access Framework.
8. **Аудіо/налаштування:** усі налаштування відтворення зі значеннями й fallback під Android; еквалайзер Android не реалізовувати.
9. **Інструменти:** перенести функції PC-бенчмарку та hybrid-експерименту в Android-еквівалент, де це можливо; замінити D3D11VA-специфічні режими Android hardware decoder режимами, чітко позначити несумісні метрики.
10. **Паритет/перевірка:** пройти кожен пункт чекліста на API 23 і новішій системі; збірка, встановлення, онлайн/офлайн, аудіо/відео, переривання, збереження/відновлення та регресія Windows збірки.

## Критерій повної версії

Кожен PC-сценарій у чеклісті має мати статус: **перенесено і перевірено на Android**, **замінено Android-еквівалентом і перевірено**, або **системно недоступно** з поясненням та альтернативою, якщо вона можлива. Повнота не означає тотожності драйверів, API, форматів чи апаратних режимів між платформами.

## Вибір архітектури

14.11.2026 користувач обрав нативний Kotlin + Media3 стек. Це означає повний порт каталогу, моделей, правил, завантажень і станів із C#; Media3 є платформним плеєром, а не YouTube extractor. ## Подальший parity-зріз

- **Тема інтерфейсу (частково виконано):** темний вигляд став типовим для нових інсталяцій і профілів без збереженої теми; явний вибір світлої теми лишається доступним і зберігається. Compose та стартова Android-тема, а також системні іконки налаштовані для темного режиму. Після встановлення APK Home перевірено знімками на фізичному Android13/API33 і Android6/API23 AVD; Settings та перемикач теми перевірено на фізичному пристрої. Повний прохід карток, діалогів, контрасту і всіх локалізацій іще потрібен.
- У Library додано channel dropdown для зведеної локальної стрічки: `All channels` або одна з локальних підписок; відписка від вибраного каналу повертає фільтр до всіх. Додано type chips All/Videos/Shorts/Live й окремий порожній стан для активних фільтрів. На API23 ручне оновлення двох тимчасових публічних підписок дало `2 channels checked · 0 failed · 2 used browse fallback`. У кеші були записи NASA та National Geographic; вибір кожного каналу показував лише його записи, Shorts для NASA — порожній результат, Videos — відео. Обидві тестові підписки/cache прибрані, попередню історію Big Buck Bunny збережено. Android13 network refresh, pagination і відновлення filter state після process death ще не перевірені. Content categories акаунта та YouTube subscriptions sync залишаються.
- На картках Home/Search додано меню More з діями Open URL та Copy URL; відкриття обмежено HTTPS YouTube-хостами. На API23 меню відображено, а Copy URL підтверджено вставкою скопійованого посилання в пошук. Open URL не натискали; плеєр не змінювався й відео не запускалось. Інші відсутні карткові дії звірити з WinForms parity-листом.
- На API23 перевірено URL-пошук прямого відео: ввід `https://www.youtube.com/watch?v=6kp91gVA9To` показав рівно одну картку з назвою, каналом, тривалістю й датою. Картку не відкривали; MediaSession лишилася `state=null`. Канали та плейлисти цим зрізом не перевірялися.

## Аналіз власного resolver-а (15.11.2026)

Поточний Android resolver має обмеження, яке впливає на реальне охоплення потоків: він приймає прямі URL та `signatureCipher` лише з уже відкритим підписом; обфускований `s` і URL-параметр `n` ще не трансформуються. Актуальна upstream-таблиця yt-dlp для YouTube-клієнтів вказує, що потоки ANDROID і WEB мають GVS PO-token policy `required`; для ANDROID також позначено рекомендований player PO token. Це пояснює, чому одних client-fallback спроб недостатньо для довгострокового resolver-а й чому HTTP 403 можливий без вирішеного token-flow. Це зовнішня діагностика протоколу, код yt-dlp не додавався до LowTube: [yt-dlp YouTube client configuration](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_base.py).

Наступний технічний етап власної реалізації: витягувати та кешувати YouTube `PLAYER_JS_URL` за версією player-а; визначати `s`/`n` challenges і виконувати тільки потрібний transform у контрольованому середовищі; дослідити власну реалізацію PO-token/attestation. Android `WebView.evaluateJavascript` наявний від API 19, тому ізольований системний WebView може бути runtime-кандидатом без стороннього resolver APK; мережу, file/content access, JS bridge і ліміти CPU/часу треба спроєктувати та перевірити до інтеграції. Офіційний API описує `evaluateJavascript` як UI-thread API та параметри блокування мережі/доступу до файлів: [WebView API](https://developer.android.com/reference/android/webkit/WebView), [WebSettings](https://developer.android.com/reference/android/webkit/WebSettings). Цей runtime ще не впроваджений; залишити Kotlin/Media3 player та API23 як цілі.

15.11.2026, перший кодовий етап resolver player-JS завершено: новий `YoutubePlayerScriptCache` приймає тільки HTTPS YouTube `/s/player/.../base.js`, забороняє redirect/інші origin, обмежує відповідь 8 MiB і тримає не більше одного скрипта в оперативному кеші.
