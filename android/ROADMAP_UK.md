Не звертався до внутрішнього consent Activity microG: upstream security advisory описує ризик підробленого тексту згоди через його експортовану Activity. Не запитував токен, не відкривав account chooser і не читав дані акаунта. Посилання: [AuthorizationClient](https://developer.android.com/identity/authorization), [GoogleAuthUtil deprecation](https://developers.google.com/android/reference/com/google/android/gms/auth/GoogleAuthUtil), [microG OAuth registration issue](https://github.com/microg/GmsCore/issues/3278), [microG consent Activity advisory](https://github.com/microg/GmsCore/security/advisories/GHSA-rp4p-8x89-jhv5).

## Ціль

Створити окремо встановлювану Android-версію LowTube як самостійний клієнт YouTube із Google-авторизацією та знайомими сценаріями основного YouTube-клієнта. Перенести **всі функції PC-версії**, крім Android-еквалайзера, або надати перевірений Android-еквівалент із чітко описаними системними обмеженнями. Windows-застосунок лишається незалежним і працездатним. Android ніколи не патчить, не підміняє і не перепаковує застосунок YouTube.

## Google-акаунт і межі YouTube API

- Профільний Google sign-in та доступ до приватних YouTube-даних — різні потоки: Profile показує системний Google account picker, потім використовує Google AuthorizationClient зі scopes `openid/email/profile` і bounded OpenID UserInfo запит. YouTube subscriptions окремо запитують `youtube.readonly`; зміни remote subscription запитують `youtube` scope лише після натискання Subscribe/Unsubscribe. Не збирати пароль і не імпортувати cookies; access token живе лише в пам’яті запиту, не зберігається й не логується. Profile поля зберігаються локально; це не серверна перевірка ID token.
- Поточний Profile/AuthorizationClient flow і YouTube AuthorizationClient consent реалізовані окремо. Для роботи власник LowTube має зареєструвати Android OAuth client для `com.lowtube.android` із SHA-1 відповідного debug/release сертифіката та ввімкнути YouTube Data API в Cloud project. Web client ID у profile flow більше не використовується. Runtime OAuth/API acceptance чекає developer-owned configuration; кінцевому користувачеві не потрібно створювати власний Cloud project.
- 19.11.2026: коли `AuthorizationClient` повертає `ApiException.CANCELED`, Profile тепер показує діагностику провайдера замість загального sign-in failure. На підключеному API33 встановлено microG 0.3.18 і його Identity `AuthorizationService`; наявність service не засвідчує успішний OAuth. Оновлений APK зібрано та встановлено; sign-in повторно не запускався, тому точна причина попереднього короткого повідомлення лишається непідтвердженою. Потрібен користувацький retry з повним результатом на екрані.
- Обраний напрям, щоб кінцевому користувачу не довелося створювати Google Cloud project: LowTube має використовувати OAuth-конфігурацію власника застосунку, підготовлену один раз для release-збірки; користувачеві залишаються звичайний Google sign-in і явна згода на YouTube scope. Це переносить налаштування на власника/оператора LowTube, але не скасовує реєстрацію Android package+signing certificate, OAuth client та YouTube Data API. Client ID не є секретом; client secret не можна вбудовувати в APK. Див. [YouTube API authorization](https://developers.google.com/youtube/data/guides/authentication) та [Google Sign-In best practices](https://developers.google.com/identity/siwg/best-practices).
- MicroG не вбудовувати в LowTube: GmsCore є системною заміною Google Play Services, для повної роботи очікує підтримку signature spoofing у ROM/системі та встановлюється як системний сервіс. Він не створює OAuth client для LowTube і не вмикає YouTube Data API, тож не знімає поточну зовнішню вимогу. Див. [microG overview](https://github.com/microg/GmsCore/wiki) та [microG installation](https://github.com/microg/GmsCore/wiki/Installation).
- Не підміняти офіційний flow входом через вбудований WebView, OAuth client ID іншого застосунку чи автоматичним вилученням браузерних cookies. Без власної LowTube OAuth-конфігурації Profile має показувати зрозумілий setup state, а гостьові можливості залишаються доступними. Офіційного варіанта без зареєстрованого OAuth client немає: API key покриває лише public-data requests, а приватні дані та зміни потребують OAuth 2.0. `GoogleAuthUtil` застарів, і Google прямо спрямовує нову авторизацію до AuthorizationClient/Credential Manager; його додавання не зніме реєстрацію client/API. Див. [YouTube API authorization](https://developers.google.com/youtube/data/guides/authentication), [GoogleAuthUtil reference](https://developers.google.com/android/reference/com/google/android/gms/auth/GoogleAuthUtil), [Google client authentication](https://developers.google.com/android/guides/client-auth).
- YouTube Data API v3 `subscriptions.list?part=snippet&mine=true` з bounded пагінацією та `subscriptions.insert/delete` реалізовані. Read-only scope запитує синхронізація; write scope `youtube` запитується лише для явної дії Subscribe/Unsubscribe. Runtime потребує ввімкненого API в Cloud project, відповідного Android OAuth client та користувацької згоди. Access token використовується тільки в пам’яті запиту. Список email-scoped, очищається після 30 днів і при sign out; sign out видаляє локальні Profile поля і намагається відкликати grant через Google revoke endpoint, коли доступний token.
- 19.11.2026: Library отримала явне завантаження власних YouTube плейлистів через `playlists.list(mine=true)` та посторінкове відкриття їхніх відео через `playlistItems.list`. Список і вміст лишаються лише у пам’яті; порядок і повтори відео зберігаються; користувач може програти послідовність або додати її до локальної черги. Обидва endpoint використовують наявний just-in-time `youtube.readonly` scope, без збереження access token. `:app:assembleDebug --no-configuration-cache` пройшла; APK встановлено й запущено на підключеному Android, MainActivity лишилася foreground. API/runtime acceptance не проводився, бо відсутня developer-owned OAuth configuration. Settled idle sample після встановлення: CPU 0%, PSS 115,6 MiB, RSS 212,5 MiB, swap PSS 0,43 MiB; точковий вимір, не benchmark. Google API не надає через `playlistItems.list` watch history та Watch Later; особисті системні плейлисти потребуватимуть окремого сумісного шляху. Документація: [playlists.list](https://developers.google.com/youtube/data/reference/rest/v3/playlists/list), [playlistItems.list](https://developers.google.com/youtube/data/reference/rest/v3/playlistItems/list).
- Офіційний YouTube Data API v3 не повертає список відео, персонально рекомендованих поточному користувачу; гостьова тематична стрічка та локальні підписки не є її еквівалентом. Див. [YouTube Data API revision history](https://developers.google.com/youtube/data/revision_history).
- Поточний пошук/стрічки використовують приватні веб-ендпоїнти; сумісність, доступ до акаунта й відповідність обраного способу отримання даних правилам треба переглянути до обіцянки повноцінної стабільності. OAuth не надає дозволу обходити обмеження API/клієнта.

## Етапи

1. **Інвентаризація:** скласти чекліст кожного PC-сценарію з джерелом у коді, даними, станами помилок та критерієм перевірки.
2. **Рішення про стек — виконано:** Kotlin + Jetpack Compose, AndroidX Media3 та окремий Kotlin backend; не переносити WPF/WinForms UI чи mpv IPC як desktop-компоненти.
3. **Окремий Android-проєкт — почато:** Kotlin/Compose проєкт із `minSdk 23`, `compileSdk/targetSdk 36`; додані Media3 1.11.0 (ExoPlayer, HLS, DASH, UI, MediaSession) і Coil. Debug APK успішно збирається та встановлюється на авторизований фізичний Android 13/API33 телефон.
   **Google account/subscriptions — реалізація готова, runtime acceptance чекає owner configuration:** Profile використовує system account picker + AuthorizationClient/OpenID UserInfo; Subscriptions окремо просить `youtube.readonly` та читає `subscriptions.list?mine=true`. Локальне сховище email-scoped, має 30-денне очищення й видалення при sign out. Власник має зареєструвати Android package/signature OAuth client і ввімкнути YouTube Data API; після цього потрібні реальні sign-in, consent і sync перевірки на API23 та API33. Sign-in не є серверно перевіреною автентифікацією.
4. **Каталог:** пошук, рекомендації, підписки, акаунтні стрічки, синхронізація, історія, канали, списки/плейлисти, Shorts і bounded paging.
5. **Медіа:** відео/audio-only, якість та формати, субтитри/доріжки, черга, наступне, resume, seek, аудіофокус, background/notification controls, recovery і діагностика.
6. **Локальна бібліотека:** локальна історія, підписки, плейлисти, resume, сумісний імпорт/експорт даних і обмежена пам'ять.
7. **Завантаження:** усі формати та правила вибору PC, черга, обмеження швидкості, прогрес, скасування/retry/resume і Android Storage Access Framework.
8. **Аудіо/налаштування:** усі налаштування відтворення зі значеннями й fallback під Android; еквалайзер Android не реалізовувати.
9. **Інструменти:** перенести функції PC-бенчмарку та hybrid-експерименту в Android-еквівалент, де це можливо; замінити D3D11VA-специфічні режими Android hardware decoder режимами, чітко позначити несумісні метрики.
10. **Паритет/перевірка:** пройти кожен пункт чекліста на API 23 і новішій системі; збірка, встановлення, онлайн/офлайн, аудіо/відео, переривання, збереження/відновлення та регресія Windows збірки.
11. **Планшетний інтерфейс — у процесі:** оптимізувати YouTube-подібний UI для планшетів, широких вікон та альбомної орієнтації. Перемикати кількість колонок карток і тип навігації за доступною шириною; для каталогу, бібліотеки, початкового setup та налаштувань застосовувати адаптивні/двопанельні макети, лишаючи телефонові компактний варіант. Підтримати split-screen і системне збільшення шрифту. Уже адаптовані стрічка, навігація, Library, Settings, Queue та Downloads; перший setup також переходить у дві незалежно прокручувані колонки від 800 dp. Queue і Downloads використовують адаптивну сітку з кількома картками на широкому вікні; компактний режим лишається одноколонковим. Перевірити всі ключові екрани на компактній, середній і розширеній ширині, різній орієнтації та API 23+.
12. **Початкове меню налаштування — основний flow реалізовано:** під час першого запуску є welcome/setup із Skip і можливістю повторно відкрити з Settings; вибір мови, масштабу UI, теми, playback max quality/H.264/30 FPS/audio-only, окремих download max quality/H.264/30 FPS, audio bitrate і SAF папки записується у спільні ключі системи налаштувань. На компактному екрані Skip/Save закріплені унизу, а налаштування прокручуються окремо; перевірено на API23/API33 AVD і фізичному API33. Широкий flow уже має дві прокручувані колонки та перевірений на API23. Далі перевірити повторне відкриття після cold start, SAF folder persistence та широкий фізичний планшет.

## Подальший parity-зріз

- **Тема інтерфейсу (частково виконано):** темний вигляд став типовим для нових інсталяцій і профілів без збереженої теми; явний вибір світлої теми лишається доступним і зберігається. ## Resolver-рішення

Користувач відхилив сторонню YTDLPDroid залежність і доручив реалізувати resolver у LowTube. Kotlin resolver використовує YouTube player response/JS та Media3 без стороннього extractor; обмежений QuickJS runtime уже підтримує `s`/`n` для перевірених шляхів. Наступні extractor етапи — підвищити сумісність між player/client versions, дослідити client/PO-token та SABR-only обмеження, далі перевіряти реальні URLs без довгого playback. Кожен тестовий перегляд обмежувати першими 2 хвилинами медіачасу.

## Аналіз власного resolver-а (15.11.2026)

Поточний Android resolver має обмеження, яке впливає на реальне охоплення потоків: він приймає прямі URL та `signatureCipher` лише з уже відкритим підписом; обфускований `s` і URL-параметр `n` ще не трансформуються. Актуальна upstream-таблиця yt-dlp для YouTube-клієнтів вказує, що потоки ANDROID і WEB мають GVS PO-token policy `required`; для ANDROID також позначено рекомендований player PO token. Це пояснює, чому одних client-fallback спроб недостатньо для довгострокового resolver-а й чому HTTP 403 можливий без вирішеного token-flow. Це зовнішня діагностика протоколу, код yt-dlp не додавався до LowTube: [yt-dlp YouTube client configuration](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_base.py).

Наступний технічний етап власної реалізації: витягувати та кешувати YouTube `PLAYER_JS_URL` за версією player-а; визначати `s`/`n` challenges і виконувати тільки потрібний transform у контрольованому середовищі; дослідити власну реалізацію PO-token/attestation. Android `WebView.evaluateJavascript` наявний від API 19, тому ізольований системний WebView може бути runtime-кандидатом без стороннього resolver APK; мережу, file/content access, JS bridge і ліміти CPU/часу треба спроєктувати та перевірити до інтеграції. Офіційний API описує `evaluateJavascript` як UI-thread API та параметри блокування мережі/доступу до файлів: [WebView API](https://developer.android.com/reference/android/webkit/WebView), [WebSettings](https://developer.android.com/reference/android/webkit/WebSettings). Цей runtime ще не впроваджений; залишити Kotlin/Media3 player та API23 як цілі.

## Resolver signature fallback — 2026-11-20

Якщо звичайний signature call-site знайдений, але його функцію не вдалося ізолювати/виконати або вона повернула непридатний URL, resolver тепер переходить до вже наявного обмеженого URL-object signature fallback. Результат і далі проходить існуючу перевірку домену/HTTPS і довжини URL; якщо fallback-кандидатів немає або вони не дають придатного signature, формат відкидається. `:app:assembleDebug` і `:app:assembleDebugAndroidTest` успішні. Після цієї зміни opt-in `YoutubeResolverPlaybackAcceptanceTest#resolvedStreamStartsAndAdvancesWithoutReachingTwoMinutes` пройшов на API23 та API33 AVD.
